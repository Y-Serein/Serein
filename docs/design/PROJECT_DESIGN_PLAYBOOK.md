# Serein-Style Project Design Playbook

最后更新：2026-05-26 10:23

这份文档沉淀的是本项目形成的设计方法，不是 Serein 专用功能清单。下次新建前端、后端、桌面、工具型或业务型项目时，可以让新项目“向这里学习”：学习目标排序、审美判断、流程闭环、架构边界、验证方式和避坑规则。

## 一句话原则

好项目不是功能堆满，而是核心路径稳定、用户知道自己在做什么、系统知道自己能安全做什么，并且每一次修改都能被验证和回滚。

## 目标排序

项目早期最容易犯的错，是把“功能很多”误判为“完成度高”。更稳的排序是：

1. 数据安全和可恢复性。
2. 高频主路径体验。
3. 用户能感知的响应速度。
4. 功能完整度。
5. UI 美观和一致性。
6. 架构优雅。

如果是工具类产品，主路径必须先到 80 分以上，再扩展周边能力。Serein 的经验是：Typora 写作体验没有稳住时，Obsidian 图谱再好也不能弥补；保存、链接、导出、窗口控制这种高频路径的小问题，会直接破坏用户信任。

## 审美方向

审美不是装饰，而是降低认知负担。

- 简洁，不等于空；信息要少而准，控件要少而明确。
- 工具型产品应安静、克制、稳定，避免营销页式大卡片和无意义装饰。
- 入口不要重复。一个功能在多个地方都出现，通常不是“方便”，而是系统没有想清楚主路径。
- 主视图优先服务用户任务，不要让说明文字、宣传文案、调试信息抢占空间。
- 视觉层级要服务操作频率：高频操作近、清楚、稳定；低频操作收进菜单或次级面板。
- 状态变化要有反馈，但不要制造“卡住”的错觉。短动作不要随便禁用按钮或显示 wait 光标。
- 图谱、统计、索引这类可视化必须反映真实数据，不能用假数据营造“高级感”。

判断 UI 是否合格，不看截图第一眼是否炫，而看用户连续操作 10 分钟是否顺、是否累、是否容易误点。

## 流程设计

流程设计的核心是减少用户脑内状态。

- 第一次打开就进入实际工作界面，不要先给无关介绍页。
- 每个核心动作都要有明确闭环：开始、执行中、成功、失败、可恢复。
- 破坏性动作必须确认，批量改写必须可预期，最好有预览或回滚。
- 错误提示要告诉用户真实失败点，不要只说“失败了”。
- 用户的下一步动作应该自然出现，而不是靠文档解释。
- 同一类工作流只保留一个主入口，其他入口必须是快捷方式，而不是并行流程。
- 不要为了展示功能而打断主流程。高级能力应渐进暴露。

Serein 的具体教训是：`[[A]]` 只有索引不够，必须能在编辑器里看见、点击、跳转、创建、失败提示；否则“功能存在”但“流程不存在”。

## 架构原则

架构的价值是让产品稳定演进，不是让代码看起来复杂。

推荐分层：

1. 领域模型层：定义业务对象、状态、索引、关系和规则，尽量纯函数。
2. IO 边界层：文件系统、网络、数据库、系统 API，只在边界处理副作用。
3. 应用编排层：把用户动作转成领域操作和 IO 调用，处理 loading/error/dirty state。
4. UI 表现层：只负责展示状态、收集输入、触发命令。
5. 验证层：用测试和手测清单覆盖主路径。

关键约束：

- 单一事实来源。不要让多个组件各自维护一份不同的业务状态。
- 副作用要集中。文件写入、网络请求、系统窗口调用不要散落在各个组件里。
- 大数据和大目录默认懒加载、分页、增量更新，不要为了实现简单递归扫全量。
- API 合约要显式。输入、输出、错误、权限、并发行为都要可预测。
- 能用纯函数测试的逻辑，不要绑死在 UI 或系统 API 里。
- 架构重构必须服务真实问题：降低风险、消除重复、提高可验证性，不能只为了“更高级”。

前端项目尤其要避免把所有逻辑堆进一个页面组件；后端项目则要避免把业务规则藏进 controller 或 SQL 拼接里。

## 前端判断标准

- 主屏就是产品，不是宣传。
- 布局稳定，点击、hover、loading 不应造成明显跳动。
- 文本、路径、错误、按钮 label 在移动端和桌面端都不能溢出。
- 键盘、鼠标、触控板路径都要考虑，高频操作不能只支持一种输入方式。
- 弹层要贴近触发点，并避免被布局上下文裁切。
- 所有按钮都要有明确 hit area；图标内部点击也应触发按钮。
- 编辑器、表格、画布、图谱这类复杂组件必须做真实交互验证。
- 性能问题优先从主线程阻塞、全量渲染、重复计算、无缓存 IO 查起。

## 后端判断标准

- 数据写入必须可确认、可失败、可恢复。
- 外部输入必须校验，不要把路径、ID、权限、格式当成可信。
- 错误要分层：用户可理解错误、日志诊断错误、程序内部错误不要混成一类。
- 批处理要考虑幂等、部分失败和重试。
- 长任务要有进度、取消或后台机制，不能阻塞主请求。
- 对外 API 不要频繁破坏兼容；必须破坏时要有迁移策略。
- 性能优化以真实瓶颈为准，不提前引入复杂缓存或队列。

## 控制论闭环

每次接手项目都按这个闭环：

1. 目标：这轮要让用户或系统达到什么状态。
2. 状态：当前已知事实是什么，来自文件、日志、测试还是用户反馈。
3. 误差：现状和目标差在哪里，哪些是主矛盾。
4. 控制动作：只调整最小必要变量。
5. 反馈：运行命令、看日志、手测、让用户验证。
6. 修正：反馈不符合预期时，先定位误差来源，再继续改。
7. 验证：用最小相关测试证明结果。
8. 沉淀：把关键决策、坑点、命令和未解问题写进 handoff/memory。

这个闭环的重点不是写漂亮流程，而是防止项目在猜测、冲动重构和局部优化里失控。

## 发布判断

内测和正式发布标准不同。

内测可以接受：

- 有已知问题。
- UI 还有细节粗糙。
- 未签名包有安全提示。
- 部分高级功能不完整。

内测不能接受：

- 数据丢失风险不可控。
- 主路径频繁卡死或崩溃。
- 用户无法判断保存、导出、删除、改写是否成功。
- 没有明确回退或复现路径。

正式发布还需要：

- 版本号、安装卸载、升级路径。
- 错误日志和用户反馈入口。
- 数据备份/迁移策略。
- 性能压力测试。
- 清晰的已知问题清单。
- 关键平台实测矩阵。

## 验证策略

验证必须贴近风险。

- 纯逻辑：单元测试。
- 类型和接口：类型检查、静态检查。
- 构建链路：生产构建。
- 系统能力：真实环境 smoke test。
- UI 体验：截图、Playwright、人工高频路径操作。
- 数据安全：复制数据集、破坏性动作回滚测试。
- 发布：干净机器安装、卸载、重装、升级测试。

不要用低层验证替代高层体验。类型检查通过，不能证明窗口按钮好点；浏览器 smoke 通过，不能证明 Tauri release 包好用。

## 常见反模式

- 把“能跑”当成“能用”。
- 把“数据结构存在”当成“工作流完成”。
- 为了修小 bug 引入大范围重构。
- 为了 UI 炫酷牺牲信息密度和稳定性。
- 多处入口重复实现同一功能。
- 把错误吞掉，只给用户一个成功假象。
- 没有真实数据集，只用空 demo 自测。
- 没有 handoff，靠对话记忆维持项目状态。
- 没有主矛盾排序，所有问题平均用力。

## 新项目提示词模板

```text
你是这个新项目的项目审核者、产品设计者和工程控制论式接手者。请先阅读项目说明、AGENTS.md/README/构建脚本/测试脚本/关键代码，不要急着改代码。

请学习 Serein 项目的设计方法：
- 目标先行，主矛盾优先。
- 数据安全和主路径体验优先于功能堆叠。
- UI 简洁克制，不做重复入口，不用装饰掩盖流程问题。
- 架构分清领域模型、IO 边界、应用编排、UI 表现和验证层。
- 每次修改按“目标→状态→误差→控制动作→反馈→修正→验证→沉淀”闭环推进。

请先输出：
1. 当前项目目标和发布阶段判断。
2. 审美/体验方向。
3. 主流程和高风险流程。
4. 架构边界和可能失控点。
5. 最小验证方案。

如果需要改代码，只做最小可回滚改动；完成后说明验证结果、风险和下一步。
```

## 迁移到任何项目时的做法

1. 先找主用户、主路径、主风险。
2. 把需求按“必须安全、必须顺、应该有、以后再说”分层。
3. 画清楚数据从哪里来、在哪里变、在哪里保存、失败怎么回滚。
4. 只为主路径设计第一屏，不为功能清单设计第一屏。
5. 建最小但真实的测试数据集。
6. 每次迭代只缩小一个主要误差。
7. 到里程碑时写 handoff 和 memory，别把经验留在脑子里。
